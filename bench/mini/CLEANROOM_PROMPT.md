You are writing a benchmark suite and a conformance test suite for "Mini", a
small language that is a strict subset of Lua 5.4. Someone else is building a
Mini implementation. Your programs will be used to measure and test it
against PUC-Lua 5.4 and LuaJIT 2.1. For the comparison to be fair, the
programs must be written independently of that implementation, from the
language specification alone.

Ground rules:
- Your only inputs are the specification in CLEANROOM/SPEC.md and the reference
  interpreters CLEANROOM/bin/lua (PUC-Lua 5.4.9) and CLEANROOM/bin/luajit (LuaJIT 2.1).
- Do NOT read, list or search anything outside CLEANROOM. In
  particular, do not look at /workspace-loimi or anything else on the
  machine to learn about the implementation. Do not search the web for
  the implementation.
- You may use your general knowledge of Lua and of well-known benchmark
  programs (the Computer Language Benchmarks Game, the classic
  interpreter benchmarks, and so on). Every program must stay inside the
  Mini subset that SPEC.md defines. Re-read the spec's restrictions
  carefully:
  - 32-bit integer range, including intermediates;
  - no metatables, no `//`, no bitwise operators, no varargs;
  - no method calls on strings;
  - multiple results are kept only in `local` and assignment statements;
  - only `pairs` and `ipairs` in generic `for`;
  - only the listed library functions, in their listed forms.



Deliverable 1: benchmarks, in CLEANROOM/bench/
- One self-contained `NAME.lua` per benchmark, with the problem size as a
  constant near the top of the file. No command-line arguments.
- Each benchmark must:
  - be deterministic;
  - print a short result or checksum, so a wrong implementation is
    detected;
  - produce byte-identical output under `bin/lua` and `bin/luajit`;
  - take roughly 1-3 seconds under `bin/lua` on this machine.
- Write `NAME.expected` with the output.
- LuaJIT is a Lua 5.1 dialect, so to keep the output identical:
  - Avoid printing floats directly; use `string.format`.
  - Avoid integer/float output differences.
  - Use only features both interpreters share. All of Mini except
    `%`-on-negative edge cases is common ground, but verify by running
    both.
- Cover at least: fib (recursive calls), binary-trees (allocation, GC),
  n-body (float arithmetic and field access), spectral-norm, fannkuch-redux
  (array permutations), and a string-building benchmark.
- Add 4-8 more of your choice that stress different interpreter paths, for
  example:
  - closures and upvalues;
  - hash-table heavy work (string keys);
  - method-call-heavy OO-style code using tables of functions, without
    metatables;
  - a sieve;
  - sorting;
  - a small interpreter or parser;
  - mandelbrot;
  - queens or other recursion and backtracking;
  - matrix multiplication.
- Write `README.md` listing each benchmark, what it stresses, its origin
  (a well-known benchmark it follows, or original), and the measured
  times under bin/lua and bin/luajit.

Deliverable 2: conformance tests, in CLEANROOM/tests/
- Small programs, about 30-60 of them, each `NAME.lua` with
  `NAME.expected`, generated by running `bin/lua`. Together they should
  cover every feature in SPEC.md systematically:
  - lexical forms;
  - arithmetic, including int/float subtypes;
  - comparisons, logic, concatenation, `#`;
  - table constructors, table semantics, border, nil removal;
  - closures and shared upvalues, including per-iteration loop variables;
  - multiple results and assignment;
  - every statement form;
  - every library function and format directive.
- The tests follow Lua 5.4 semantics, so they only need to match bin/lua,
  not luajit. They must still stay strictly inside the Mini subset. Do not
  test behaviour the spec calls unspecified, such as `pairs` order (sort
  keys before printing), table/function addresses, overflow, or error
  message text.
- Error behaviour: a few tests may check that something errors. Name them
  `err_*.lua`, and make `.expected` hold only the output printed before
  the error. The harness checks the nonzero exit status.

When done, reply with:
- a summary of what you wrote;
- the timing table;
- any places where SPEC.md was ambiguous or where you were unsure whether
  something is in the subset. This is important feedback for the spec.
