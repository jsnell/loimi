# 7. Heap objects and the GC

Pip gets strings and arrays, which live in a garbage-collected heap:

```text
let a = [1, 2.5, "three", nil, [4, 5]];
print a[4][1];                 // 5
print "n = " + len(a);         // n = 5
let r = array(3);              // [nil, nil, nil]
r[0] = "x" + r[1];             // xnil
```

The collector is `std.gc`, a precise, non-moving mark-sweep collector
written in Loimi. The language's part is to know what is a reference,
to generate the tracing code, and to make sure that whenever a
collection can happen, everything it needs to see is visible.

Code: [`examples/tutorial/step7/`](../../examples/tutorial/step7).

## Objects

```loimi
/// A string: its bytes are a trailing array, allocated with the object.
pub object Str { data: [u8] }

/// An array of a fixed length.
pub object Arr { items: [Value] }
```

An `object` is a GC-managed struct. The compiler adds the header (type
id, mark bit) and generates the function that traces it from the field
types: `Str` has nothing to trace, `Arr` traces each item, and a `Value`
traces whichever variants hold references. The last field may be a
trailing array whose length is given at allocation.

References are `Gc<T>`, and `Value` gets two variants that hold them:

```loimi
pub value Value repr nanbox {
    Num(f64) unboxed,
    Int(i32),
    Nil,
    Bool(bool),
    Fn(*Proto),
    Str(Gc<Str>),
    Arr(Gc<Arr>),
}
```

`new(heap, Obj { fields }, n)` allocates, with `n` the length of the
trailing array:

```loimi
/// A new string holding a copy of `s`. Allocation never collects, so
/// this function has no effects.
pub fn new_str(h: *gc.Heap, s: str) -> Gc<Str> {
    let o = new(h, Str {}, s.len);
    mem.memcpy(o.data.ptr, s.ptr, s.len);
    o
}
```

## Allocation never collects

This is the most important design decision in `std.gc`, and it differs
from most C collectors. In Lua, CPython or a typical JS engine, any
allocation may trigger a collection, so every function that allocates
must keep every live reference visible to the collector, at every
allocation. That is where most GC bugs in C interpreters come from.

In `std.gc`, allocation only allocates. Collections happen at explicit
**safepoints**: calls to functions declared `uses gc`, such as
`gc.collect` and `gc.maybe_collect`. The interpreter decides where those
are, typically just before an op allocates, and the compiler knows
exactly which calls may collect.

## Roots

When a collection runs, the collector must find every reference the
program can still use. In Pip those are:

- the registers of every active call,
- the constants of every function (string literals are constants),
- the global variables,
- local variables of host functions that hold references across a
  safepoint.

The first three are the interpreter's own data structures, so the
interpreter tells the heap how to find them, with a **root scanner**:

```loimi
/// The GC's roots: every active frame's registers, every function's
/// constants, and the globals. Registered with `heap.add_scanner`; it runs
/// during a collection, so it has no effects and cannot collect.
pub fn scan_roots(h: *gc.Heap, data: *u8) {
    let m = data as *Machine;
    var f = m.frames;
    while f <= m.fp {
        for i in 0..f.proto.nregs as u64 { gc_mark(h, f.base[i]); }
        f = f + 1;
    }
    for i in 0..m.protos.len {
        let p = m.protos.at(i);
        for j in 0..p.consts.len { gc_mark(h, p.consts[j]); }
    }
    for i in 0..m.globals.cap {
        if m.globals.slots[i].key != 0 { gc_mark(h, m.globals.slots[i].value); }
    }
}
```

```loimi
    m.protos = &prog.protos;
    m.heap.add_scanner(&m as *u8, vm.scan_roots);
    if stress { m.heap.set_stress(true); }
```

`gc_mark` marks whatever a `Value` (or `Gc<T>`) refers to; the
generated trace functions do the rest. The scanner's type,
`fn(*gc.Heap, *u8)`, has no effects, so a scanner that tried to
collect would not compile.

The scanner walks the frames up to `m.fp`. But the current frame is in
the `fp` *register*, a state variable, and the machine's copy is only as
fresh as the last time someone stored it. That is the problem Lua's
`savepc` and `Protect()` solve by hand.

## Effects and `sync`

A function that may collect says so with `uses gc`. Forget it, and the
compiler stops you at the call:

```loimi
/// ADD, SUB and MUL outside their fast paths. `+` with a string on either
/// side joins the two as text, which allocates, so it may collect first.
fn arith_slow(m: *Machine, op: Arith, a: Value, b: Value) -> Result<Value, str> uses gc {
    if op == Arith.Add and (is_str(a) or is_str(b)) {
        // `a` and `b` hold traced values and are used after this call,
        // so the compiler registers them as roots while it runs.
        gc.maybe_collect(&m.heap);
        m.tmp.clear();
        value.write(&m.tmp, a);
        value.write(&m.tmp, b);
        return Ok(Value.Str(value.new_str(&m.heap, m.tmp.as_str())));
    }
    arith(op, a, b)
}
```

```text
error: `maybe_collect` uses gc, but `arith_slow` does not declare it; add `uses gc` to its signature
  --> vm.lm:173:9
  173 |         gc.maybe_collect(&m.heap);
      |         ^^^^^^^^^^^^^^^^^^^^^^^^^
```

The effect does two things:

- **In ordinary functions**, traced locals that are in scope at a
  `uses gc` call are registered in a shadow-stack frame, which the
  collector scans. Here `a` and `b` stay alive across `maybe_collect`.
  Only paths that call an effectful function pay for this, and those are
  slow paths by nature.
- **In handlers**, which may call effectful functions without declaring
  anything, the compiler runs the vm's `sync` block before each such
  call:

```loimi
    // Before a call that may collect, the compiler runs this, so that the
    // root scanner sees the current frame.
    sync { ctx.fp = fp; }
```

Calls without effects pay nothing: the hot path never stores `fp`.
Handler locals holding references are rooted at effectful calls too.

There are three effects, in order: `sync` (the callee reads vm state,
for example to build a traceback), `gc` (it may collect; implies
`sync`) and `reenter` (it may run guest code). Function types carry
them as well (`fn(*Heap) uses gc`), so a call through a pointer is
checked like a direct call.

One rule to remember: traced *temporaries* are not roots. If you build
a value, call something that may collect, and then use the value, bind
it to a local first.

## Safepoints in handlers

The ops that allocate check the heap's budget inline and collect in a
cold block, so the test is two loads and a compare and the collection
(with its sync) is out of the fast path:

```loimi
    /// R[dst] = [R[base], ..., R[base+n-1]]
    op NEWLIST(dst: reg, base: reg, n: listn) : ABC {
        // Collect, if enough has been allocated, before allocating. The
        // test is inline; the collection, and the sync before it, are cold.
        if unlikely(ctx.heap.allocated > ctx.heap.threshold) { cold { gc.collect(&ctx.heap); } }
        let arr = new(&ctx.heap, value.Arr {}, n);
        for i in 0..n { arr.items[i] = regs[base.raw + i]; }
        dst = Arr(arr);
        next
    }
```

The collection happens before the allocation, while the elements are
still only in registers, which the scanner sees. There is no write
barrier on `arr.items[i] = ...`: the mark-sweep policy does not need
one.

## Stale registers

There is one more subtle root problem. A callee's register window
starts above the caller's live registers, in memory that earlier calls
used. Those slots may still hold references to objects that were
collected since, because nothing was scanning them. When the new frame
becomes active the scanner would read them and mark freed memory. So
CALL clears the callee's registers past its arguments:

```loimi
            // Registers past the arguments still hold whatever an earlier
            // call left there, possibly objects the collector has freed
            // since. The root scanner will read them, so clear them.
            var i = n as u64;
            while i < p.nregs as u64 {
                callee[i] = Nil;
                i += 1;
            }
```

(Mini tried clearing lazily instead, in the scanner. It was faster on
some benchmarks and slower on others, and was dropped as "not worth the
GC subtlety".)

## GC stress

A missing root is a bug that shows up only when a collection happens at
exactly the wrong moment, which in a normal run may be never: Pip's
tests allocate far less than the 1 MiB budget before the first
collection. Stress mode collects at every safepoint instead:

```text
./pip tests/garbage.pip --gc-stress
```

Every test in steps 7 to 9 runs twice, normally and with
`--gc-stress`, in all three dispatch modes. To see what this catches,
comment out the line that marks the globals in `scan_roots` and run
`tests/garbage.pip`. Without stress the output is right, because no
collection happens. With stress:

```text
[[[[[[...], r199], r199], r199], r199], r199]
```

instead of `[[[[[], r0], r50], r100], r150]`: the global array was
freed and its memory reused for other strings.
