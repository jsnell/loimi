# 7. Heap objects and the GC

Pip gets strings and arrays, which live in a garbage-collected heap:

```text
let a = [1, 2.5, "three", nil, [4, 5]];
print a[4][1];                 // 5
print "n = " + len(a);         // n = 5
let r = array(3);              // [nil, nil, nil]
r[0] = "x" + r[1];             // xnil
```

The collector is `std.gc`: a precise, non-moving mark-sweep collector
written in Loimi. The language's part of the work is to:

- know which values are references
- generate the code that traces objects
- make sure that whenever a collection can happen, the collector can
  see every reference it needs to

The code is in [`examples/tutorial/step7/`](../../examples/tutorial/step7).

## Objects

```loimi
/// A string: its bytes are a trailing array, allocated with the object.
pub object Str { data: [u8] }

/// An array of a fixed length.
pub object Arr { items: [Value] }
```

An `object` is a struct managed by the GC. The compiler adds a header
(a type id and a mark bit). It also generates the function that traces
the object, from the field types:

- `Str` has nothing to trace.
- `Arr` traces each item.
- A `Value` traces whichever variants hold references.

The last field may be a trailing array, whose length is given when the
object is allocated.

References are `Gc<T>`, and `Value` gets two variants that hold them:

```loimi
pub value Value repr nanbox {
    Num(f64) unboxed,
    Int(i32),
    Nil,
    Bool(bool),
    Fn(*Proto),
    Str(Gc<Str>),
    Arr(Gc<Arr>),
}
```

`new(heap, Obj { fields }, n)` allocates an object, where `n` is the
length of the trailing array:

```loimi
/// A new string holding a copy of `s`. Allocation never collects, so
/// this function has no effects.
pub fn new_str(h: *gc.Heap, s: str) -> Gc<Str> {
    let o = new(h, Str {}, s.len);
    mem.memcpy(o.data.ptr, s.ptr, s.len);
    o
}
```

## Allocation never collects

This is the most important design decision in `std.gc`, and it is
different from most C collectors. In Lua, CPython or a typical
JavaScript engine, any allocation may start a collection. So every
function that allocates must keep every live reference visible to the
collector at every allocation. That is where most GC bugs in C
interpreters come from.

In `std.gc`, allocation only allocates. Collections happen only at
**safepoints**: calls to functions declared `uses gc`, such as
`gc.collect` and `gc.maybe_collect`. The interpreter decides where the
safepoints are, usually just before an op allocates. The compiler knows
exactly which calls may collect.

## Roots

When a collection runs, the collector must find every reference the
program can still use. In Pip those are:

- the registers of every active call
- the constants of every function (string literals are constants)
- the global variables
- local variables of Loimi functions that hold references across a
  safepoint

The first three are the interpreter's own data structures, so the
interpreter tells the heap how to find them, with a **root scanner**:

```loimi
/// The GC's roots: every active frame's registers, every function's
/// constants, and the globals. Registered with `heap.add_scanner`; it runs
/// during a collection, so it has no effects and cannot collect.
pub fn scan_roots(h: *gc.Heap, data: *u8) {
    let m = data as *Machine;
    var f = m.frames;
    while f <= m.fp {
        for i in 0..f.proto.nregs as u64 { gc_mark(h, f.base[i]); }
        f = f + 1;
    }
    for i in 0..m.protos.len {
        let p = m.protos.at(i);
        for j in 0..p.consts.len { gc_mark(h, p.consts[j]); }
    }
    for i in 0..m.globals.cap {
        if m.globals.slots[i].key != 0 { gc_mark(h, m.globals.slots[i].value); }
    }
}
```

```loimi
    m.protos = &prog.protos;
    m.heap.add_scanner(&m as *u8, vm.scan_roots);
    if stress { m.heap.set_stress(true); }
```

`gc_mark` marks whatever a `Value` (or `Gc<T>`) refers to, and the
generated trace functions do the rest. The scanner's type,
`fn(*gc.Heap, *u8)`, has no effects, so a scanner that tried to collect
would not compile.

There is a catch. The scanner walks the frames up to `m.fp`, but the
current frame is in the state variable `fp`, which lives in a machine
register. The copy in `Machine` is only as up to date as the last time
something stored it. This is the problem Lua's `savepc` and `Protect()`
solve by hand.

## Effects and `sync`

A function that may collect says so with `uses gc`. Forget it, and the
compiler stops you at the call:

```loimi
/// ADD, SUB and MUL outside their fast paths. `+` with a string on either
/// side joins the two as text, which allocates, so it may collect first.
fn arith_slow(m: *Machine, op: Arith, a: Value, b: Value) -> Result<Value, str> uses gc {
    if op == Arith.Add and (is_str(a) or is_str(b)) {
        // `a` and `b` hold traced values and are used after this call,
        // so the compiler registers them as roots while it runs.
        gc.maybe_collect(&m.heap);
        m.tmp.clear();
        value.write(&m.tmp, a);
        value.write(&m.tmp, b);
        return Ok(Value.Str(value.new_str(&m.heap, m.tmp.as_str())));
    }
    arith(op, a, b)
}
```

```text
error: `maybe_collect` uses gc, but `arith_slow` does not declare it; add `uses gc` to its signature
  --> vm.lm:173:9
  173 |         gc.maybe_collect(&m.heap);
      |         ^^^^^^^^^^^^^^^^^^^^^^^^^
```

The effect does two things:

- **In ordinary functions**, local variables that hold references and
  are in scope at a `uses gc` call are registered as roots while the
  call runs. Here, that keeps `a` and `b` alive across `maybe_collect`.
  Only code that calls a `uses gc` function pays for this, and such
  code is a slow path anyway.
- **In ops**, which may call `uses gc` functions without declaring
  anything, the compiler runs the vm's `sync` block before each such
  call:

```loimi
    // Before a call that may collect, the compiler runs this, so that the
    // root scanner sees the current frame.
    sync { ctx.fp = fp; }
```

Calls without effects cost nothing extra: the hot path never stores
`fp`. Local variables in ops that hold references are also rooted at
`uses gc` calls.

There are three effects. Each includes the one before it:

| Effect | Means the function may |
|---|---|
| `sync` | read vm state, for example to build a traceback |
| `gc` | collect garbage (includes `sync`) |
| `reenter` | run guest code |

Function types carry effects too (`fn(*Heap) uses gc`), so a call
through a function pointer is checked like a direct call.

Entries follow the same rule. Once an op may collect, so may any call
of the entry, and the entry must say so in its signature:

```loimi
    entry run(m: *Machine, main: *Proto) -> Result<(), str> uses gc {
```

```text
error: entry `run` runs vm code that may collect, so its callers must root their traced locals: declare it `entry run(..) -> Result<(), str> uses gc`
```

`Pip.run` then has the type `fn(*Machine, *Proto) -> Result<(), str>
uses gc`. Its callers, here `main`, must declare the effect too. It
can't be stored in a function pointer type without the effect, since a
call through that pointer would root nothing.

One rule to remember: *temporaries* are not roots, only local
variables. If you build a value, call something that may collect, and
then use the value, bind it to a local first.

## Safepoints in handlers

The ops that allocate check the heap's budget in the op, and collect in
a cold block. So the fast path pays only for the test, two loads and a
compare. The collection, and the sync before it, are out of the way:

```loimi
    /// R[dst] = [R[base], ..., R[base+n-1]]
    op NEWLIST(dst: reg, base: reg, n: listn) : ABC {
        // Collect, if enough has been allocated, before allocating. The
        // test is inline; the collection, and the sync before it, are cold.
        if unlikely(ctx.heap.allocated > ctx.heap.threshold) { cold { gc.collect(&ctx.heap); } }
        let arr = new(&ctx.heap, value.Arr {}, n);
        for i in 0..n { arr.items[i] = regs[base.raw + i]; }
        dst = Arr(arr);
        next
    }
```

The collection happens before the allocation, while the elements are
still only in registers, where the scanner sees them.

This cold block doesn't end in a control word: it falls through to the
rest of the op. The compiler copies the rest of the op, which ends in
`next`, into the cold block, so the block can still be moved out of the
op.

Don't put this check in a vm function such as `fn gc_point() { .. }`.
There the compiler has no rest of the op to copy, so the cold block
stays in place, and its call can give the op a stack frame on every
run. Write the check in the op itself. (Or end the cold block with
`redo`. That is safe when the check is the op's first statement,
because after a collection the budget test is false.)

`loimi build --release -W handler_frame` reports ops whose fast path
got a stack frame, and the calls that caused it.

When an op stores a reference into an object, such as
`arr.items[i] = ...` in SETINDEX, the compiler adds a write barrier.
It is for `std.gc`'s optional generational mode
(`heap.set_generational(true)`), which Pip does not turn on. In a plain
mark-sweep heap, the barrier is a test of one header byte.

## Stale registers

There is one more subtle root problem. A callee's registers start
above the caller's, in memory that earlier calls used. Those slots may
still hold references to objects that have since been freed, because
nothing was scanning them. Once the new frame is active, the scanner
would read them and mark freed memory. So CALL clears the callee's
registers past its arguments:

```loimi
            // Registers past the arguments still hold whatever an earlier
            // call left there, possibly objects the collector has freed
            // since. The root scanner will read them, so clear them.
            var i = n as u64;
            while i < p.nregs as u64 {
                callee[i] = Nil;
                i += 1;
            }
```

## GC stress

A missing root is a bug that shows up only when a collection happens at
exactly the wrong moment. In a normal run that may be never: Pip's
tests allocate far less than the 1 MiB budget before the first
collection. Stress mode collects at every safepoint instead:

```text
./pip tests/garbage.pip --gc-stress
```

Every test in steps 7 to 9 runs twice, normally and with
`--gc-stress`, in all three dispatch modes.

To see what this catches, comment out the line that marks the globals
in `scan_roots`, and run `tests/garbage.pip`:

- Without stress, the output is right, because no collection happens.
- With stress, the program crashes with a segmentation fault instead of
  printing `[[[[[], r0], r50], r100], r150]`. The global array was
  freed and its memory reused.

What a missing root does depends on what reuses the memory. It can
also print wrong data instead of crashing.

A crash tells you that something is wrong, but not where. `loimi build
--gc-check-roots` builds a collector that fills freed objects with a
byte pattern, and checks every reference it is given before reading the
object. That covers the roots the compiler registers, the copies of vm
state, `gc_mark` calls in scanners, and traced fields.

With the globals line still commented out, the stress run stops at the
first collection that reaches the freed array. Here it reaches it
through a frame register that still holds it:

```text
$ loimi build main.lm --gc-check-roots -o pip-check
$ ./pip-check tests/garbage.pip --gc-stress
gc check-roots: bad reference 0x00007fbd68c002f0: a freed object
  gc_mark in vm.scan_roots at vm.lm:89:44
```

The report names the root the reference came through, and where. For a
local variable that the compiler rooted, it names the function, the
call and the variable's slot.
